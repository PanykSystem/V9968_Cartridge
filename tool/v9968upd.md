# V9968upd
	MSX-DOS上で動作する V9968 Cartridge Update Tool である。
	実行ファイル名は V9968UPD.COM である。

# Usage
	/H, /? が指定された場合、あるいは引数なしの場合には Usage が表示される。
	System Control にアクセスし、V9968 Cartridge が装着されていない場合は、
	その旨表示して DOSへ戻る。

	> V9968UPD
		引数無しで起動し、かつ V9968 Cartridge を検知した場合は、
		ConfigROM のバージョン情報を表示する。

		Cfg. Ver: {Config data バージョン情報文字列}

	> V9968UPD V9968cfg.bin
		V9968cfg.bin が、V9968 Cartridge用の Config data であるか確認し、
		Config data であると認知した場合に、ConfigROM の 000000h- にその内容を書き込む。
		Config data には、専用のヘッダをつけて置き、それで認知する。
		書き込むデータはそのヘッダの後についている。
		そして、対応する Config data のバージョンを 7DFF00h- に書き込む。

	/C, /B はサポートしない。ファイル名を直接指定する。
	ファイル名は MSX-DOS の 8.3 形式で、A: などのドライブ指定が可能。
	引数やファイル名の英字は大文字・小文字を区別しない。

	更新時は System Controller の capability (4Fh) が A1h の場合だけ
	Page mode を使用し、それ以外は Legacy mode を使用する。実行時に
	`Mode    : Page accelerated` または `Mode    : Legacy byte` を表示する。
	Legacy mode は従来の byte 単位の書き込みを使用するため、旧 FPGA と互換。

	Page mode は最大 256 byte を 1 回の Page Program で書き込み、完了まで
	SR1 の BUSY をポーリングする。ページ境界をまたぐ書き込みと読み出しは
	自動的に分割し、全 FFh の書き込みページは省略する。ベリファイはページ
	読み出しを使用して全バイトを比較する。ページ転送 result が 01h の場合は
	エラー終了し、再試行しない。ページコマンドは 43h-45h の開始アドレスを
	自動更新しない。

	高速化には FPGA と V9968UPD.COM の両方の更新が必要。
	旧 FPGA に新しいツールだけを入れた場合は Legacy mode のままである。
	まず USB 接続の GOWIN Programmer で新 FPGA を書き込み、Page mode 表示を確認する方法を推奨する。
	tool/config の既存 V9968CFG.BIN は自動更新されない。新しい FPGA イメージを用意し、
	mk.bat でヘッダ付き更新ファイルを生成すること。

	256 バイトすべてが FFh 以外のテストでは、本体の Page Program 回数は従来の 256 回から
	1 回になる。これは書き込みコマンド回数の削減であり、実際の所要時間が 256 分の1になる
	ことを保証するものではない。DOS のファイル読み出し、消去、I/O 転送時間などは別途かかる。
	SPI クロックは信頼性向上のため約53.7MHzから約26.85MHzへ下げる。
	不定アドレスの Verify error の原因を実機で特定できたわけではなく、3台での再確認が必要。

	ConfigROM の 7DFF00h- の 16byte には Config data のバージョン情報文字列
	が記録される。
	バージョン領域の 64KB ブロック (7D0000h-7DFFFFh) は専用領域とし、
	Config data 本体のサイズは 1-7D0000h byte に制限する。
	バージョン更新時はこのブロックを消去し、16byte のバージョン情報だけを書き込む。
	BIOS データ・BIOS バージョンの読み書きは行わない。

# Config data header
	+0	"V9968_TN20K_CARTRIDGE" (残り +31 までは 00h を詰める)
	+32	Config data バージョン情報文字列
	+48	Config data 本体

	シグネチャは 00h パディングを含む 32byte 全体を比較する。
	ヘッダは書き込まず、+48 以降を ConfigROM の 000000h- に書き込む。
	バージョン情報は 16byte 固定長で、短い文字列は 00h で終端する。

# ソースコード
	MITライセンスのヘッダを冒頭に付け、ZMA でアセンブルできる Z80プログラムとする

# ビルド
	zma.exe 使ってアセンブルし、V9968UPD.COM を生成する
	tool の build.bat を実行する。カレントディレクトリによらずビルド可能。

	zma.exe v9968upd.asm V9968UPD.COM

# 自動テスト
	Python と z80 パッケージを使用し、生成した V9968UPD.COM 自体を
	Z80 エミュレータ上で実行する。MSX-DOS と System Controller はテスト用モデルを使う。
	リポジトリルートで次を実行する。

	python -m unittest discover -s tool -p test_v9968upd.py -v

	引数・デバイス検出・シグネチャ・サイズ・消去・書き込み・ベリファイ・
	バージョン更新・16KB/64KB 境界・異常時のバージョン保持に加え、
	旧 FPGA の Legacy mode、新 FPGA の Page mode、1/255/256/257 byte と
	16KB/64KB のページ境界、密なデータの書き込み回数削減、ページ転送失敗・タイムアウト、
	破損書き込み時の診断を確認する (13テスト)。
	実機での動作確認は別途必要。

# ベリファイ失敗時の表示
	不一致を検出すると、Flash のアドレス、期待値、実読値、および直前の完了待ちで読んだ
	ステータスレジスタ1の値を表示して終了する。表示例:

	Verify error at 7E0000h: expected 41h, read FFh (last SR1=00h).

	この例では 7E0000h に 41h を期待したが FFh が読めたことを示す。
	last SR1 は直前の書き込み・消去の完了待ちで最後に読み取った値であり、
	不一致アドレスへの書き込み直後の値とは限らない。
	ベリファイ失敗時は、バージョン領域を更新しない。

	消去では、各ブロックについて次の 2 点を確認し、満たさなければその時点でエラー終了する
	（書き込みもバージョン更新も行わない）。
	- 消去コマンド後の完了待ちで BUSY=1 を一度でも観測したこと。64KB 消去は数ms 以上かかるため、
	  観測できない場合は ConfigROM がコマンドを無視した（書き込み保護など）とみなす。
	    Erase was not accepted (BUSY never set, SR1=00h).
	- ブロック先頭 256 バイトが FFh であること（簡易ブランクチェック）。
	    Erase check failed at 7E0000h: read 41h (last SR1=00h).
	消去時の OK は上記を満たしたことを示すもので、ブロック全バイトの検査ではない。
	ConfigROM 更新失敗時は Flash 内の ConfigROM が未完成の可能性があるため、
	再度書込みを試行するか、USBコネクタから GOWIN Programmer で書き込むこと。
